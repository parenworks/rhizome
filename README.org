* Rhizome

StumpWM-style window manager for the [[https://github.com/riverwm/river][River]] Wayland compositor, written in Common Lisp.

The goal: a Wayland desktop/window manager like [[https://github.com/YaLTeR/niri][niri]] but written in Common Lisp and as programmatically syntactic as [[https://github.com/stumpwm/stumpwm][StumpWM]]. Live REPL-driven window management, programmable hooks, a native CL app launcher rivaling [[https://codeberg.org/dnkl/fuzzel][fuzzel]], and the legacy and spirit of systems like Harmony from the Lisp Machines.

* Architecture

#+begin_example
WSLg (Weston) → River (nested) → Rhizome (window manager)
#+end_example

On a real Linux machine (e.g. Arch Linux):

#+begin_example
DRM/KMS → River (compositor) → Rhizome (window manager)
#+end_example

River is a non-monolithic Wayland compositor — it handles rendering and input hardware, but delegates all window management policy to a separate process via the =river-window-management-v1= protocol. Rhizome is that process. This is exactly the StumpWM model: StumpWM doesn't composite, it manages windows on top of X11. Rhizome does the same on top of Wayland/river.

The protocol uses a **manage/render sequence loop**:

1. River sends state changes (new window, output, seat) then =manage_start=
2. Rhizome sends window management decisions (propose dimensions, focus, fullscreen) then =manage_finish=
3. River sends actual window dimensions then =render_start=
4. Rhizome sends rendering decisions (position, borders, z-order) then =render_finish=

This gives StumpWM-style live REPL control — you can redefine layouts, switch focus, and add commands without restarting the compositor.

** Protocol interfaces

- =river_window_manager_v1= — global factory, manages the sequence loop
- =river_window_v1= — individual windows (propose dimensions, fullscreen, close, borders, tiled state, hide/show)
- =river_output_v1= — outputs/monitors (position, dimensions, presentation mode)
- =river_seat_v1= — input seats (focus windows, pointer bindings, interactive move/resize)
- =river_node_v1= — render list nodes (set position, place above/below for z-ordering)
- =river_shell_surface_v1= — surfaces for WM UI (status bars, launchers, backgrounds)
- =river_decoration_v1= — window decorations above/below content
- =river_pointer_binding_v1= — pointer button bindings with modifiers
- =river_xkb_bindings_v1= — keyboard bindings with xkb keysyms and modifier lists
- =zwlr_layer_shell_v1= — wlr layer shell protocol for overlay surfaces (launcher)
- =wl_compositor= — Wayland compositor for creating surfaces
- =wl_shm= — shared memory buffers for rendering
- =wl_seat= — raw keyboard input for the launcher

** Key Wayflan quirks discovered

- Bitfield enums expect keyword lists, not integers (e.g. =(:mod1)= for Alt, =(:keyboard)= for seat capabilities)
- Regular enums expect keywords (e.g. =:top= for layer, =:exclusive= for keyboard interactivity)
- =wl-registry.bind= requires the interface class from =wl:find-interface-named=
- The registry proxy must be kept globally; creating new registries causes GC'd proxy errors
- CFFI string decoding errors from Wayflan can crash the WM — wrap =wl-display-dispatch-event= in =handler-case=

** Session integration (REQUIRED for a daily driver)

Five session-level pieces make rhizome behave like a first-class
desktop. Without them everything *looks* fine until you touch the
parts that talk to the session bus:

1. *Session environment* (~/.local/bin/rhizome-session, exported
   before river starts): =XDG_CURRENT_DESKTOP=river=,
   =XDG_SESSION_TYPE=wayland=, and — mirroring Omarchy's Hyprland
   envs.lua — =QT_QPA_PLATFORMTHEME=gtk3= (Qt apps follow the GTK
   theme: without it qBittorrent and every Qt app render light no
   matter what you select), plus the native-Wayland forcing set
   (=GDK_BACKEND=, =QT_QPA_PLATFORM=, =MOZ_ENABLE_WAYLAND=,
   =ELECTRON_OZONE_PLATFORM_HINT=, =OZONE_PLATFORM=).

2. *Environment import* (~/.config/river/init, guarded on
   =XDG_CURRENT_DESKTOP=river=): =systemctl --user
   import-environment WAYLAND_DISPLAY ...= and
   =dbus-update-activation-environment --systemd ...=, then
   =systemctl --user restart xdg-desktop-portal=. Without this,
   D-Bus-ACTIVATED processes (portal backends: file choosers, app
   launchers, flatpak helpers) inherit a stale activation
   environment from the previous session and die trying to connect
   to a dead display — Steam's add-library-folder picker and every
   portal dialog silently never appears. The import must NOT run
   in a nested test river (it would poison the outer session's
   activation environment); the XDG_CURRENT_DESKTOP guard prevents
   exactly that. Distro-layer env vars (e.g. =OMARCHY_PATH=, which
   Omarchy's sleep-lock conditions on) ride along when set — a
   no-op elsewhere. The import is followed by =systemctl --user
   start rhizome-session.target= (see 4).

3. *Portal backends* (~/.config/xdg-desktop-portal/river-portals.conf):
   =FileChooser=omanta=, =default=gtk=, =Secret=gnome-keyring= —
   the same backends the Hyprland session pins, so pickers and
   secrets behave identically across sessions.

4. *Systemd graphical session* (~/.config/systemd/user/
   rhizome-session.target, started by river init after the
   environment import): the stock =graphical-session.target= refuses
   manual starts (dependency-only by design; compositors launched
   via uwsm get it for free), so the anchor target simply =Wants= it.
   Starting the anchor brings up every service your distro has
   enabled for =graphical-session.target= — on Omarchy that's
   fcitx5, sleep-lock, crash-watch, bt-agent and friends; on a bare
   install, nothing (harmless). On compositor exit, rhizome-session
   stops the anchor; =graphical-session.target='s
   =StopWhenUnneeded=yes= then tears it and its =PartOf= services
   down (mirroring uwsm's cleanup).

5. *Polkit agent* (~/.config/river/init session-apps block):
   =lxqt-policykit-agent=, pgrep-guarded so river restarts never
   spawn duplicates. Without a registered agent, polkit falls back
   to a textual prompt that cannot appear under Wayland, so every
   GUI privilege prompt (pkexec, power actions) fails silently.
   Note: hyprpolkitagent does NOT work here — its embedded Hyprland
   toolkit binds =xdg_wm_base= at v5 max while river advertises v6,
   a fatal registry error. And pgrep -x cannot match its 19-char
   name (the kernel truncates comm at 15), hence the =pgrep -f=
   guard.

All five pieces live in =session/= in this repo — =river-init=,
=rhizome-session=, =rhizome-cmd=, =rhizome-session.target=,
=river-portals.conf= — and =session/sddm/= carries the SDDM session
entry that launches rhizome-session (an Omarchy-specific installer;
see the next section for everyone else).

** Installing on any distribution

Everything above is plain shell and systemd user units — nothing in
the session wiring is tied to one distribution or one desktop
layer. Run =bash session/install.sh= to install the whole set into
=$HOME=; re-running it is safe. The greeter entry is separate:
Omarchy+SDDM users run =session/sddm/install-root.sh= with sudo,
everyone else points their display manager (or a TTY) at
=~/.local/bin/rhizome-session=.

*** Distro substitutions

The reference setup defaults below come from the development
machine (Arch + Omarchy). Substitute per your system:

1. *Portal file chooser*: =river-portals.conf= pins
   =FileChooser=omanta= (Omarchy's picker) — elsewhere the file
   picker breaks. Point it at a backend you actually have (=gtk=
   or your flatpak portal), and install =xdg-desktop-portal= plus
   that backend. =Secret=gnome-keyring= likewise needs
   gnome-keyring installed and unlocked.
2. *Greeter*: =session/sddm/= is Omarchy-specific (the greeter
   theme, =omarchy pkg add=, SDDM autologin parking). Skip it and
   register the session with your own DM: greetd, ly, lightdm, or
   GDM all accept the same =Exec=. On distros where river is not
   at =/usr/bin/river= (NixOS), fix the desktop =TryExec= too.
3. *Session services*: the =rhizome-session.target= anchor starts
   whatever =graphical-session.target.wants/= holds on your
   machine — nothing on a bare install. The =OMARCHY_PATH= import
   is conditional (only when set) and the =systemctl= lines in
   river-init no-op cleanly on non-systemd distros.
4. *Session apps* (river-init's session-apps block): =variety=
   (wallpaper), =flameshot= (bar screenshot button),
   =lxqt-policykit-agent= (GUI auth prompts). Missing ones just
   fail to spawn — install them or trim the block.
5. *Power actions*: MOD+Shift+Q/R and suspend/hibernate shell out
   to =systemctl=. On systemd distros that works (polkit prompts
   via the agent above); on non-systemd distros (Void, Artix/runit,
   Guix) it fails — patch =commands.lisp= for =poweroff=/=reboot=
   or elogind's =loginctl=.
6. *Qt theming*: =QT_QPA_PLATFORMTHEME=gtk3= needs your distro's
   Qt-gtk platformtheme plugin; without it Qt apps merely fall
   back to their default theme.

The development machine's extras, all optional and clearly

** Live eval prompt (MOD+;)

A small centered prompt opens; type a Lisp expression and press Enter to
evaluate it in the *running WM image* — redefine layouts, change state,
inspect anything, without restarting the compositor. The keyboard handler
tracks shift state (extended evdev-to-xkb mapping), so parens, quotes and
colons are typeable. Results display in the prompt and log to the WM log;
errors are caught and shown instead of killing the WM. Escape closes the
prompt.

#+begin_src lisp
;; Examples typed into the prompt (implicit RHIZOME package):
(+ 1 2)                          ; => 3
*workspace-count*                ; => 9
(switch-workspace 3)             ; immediate effect
#+end_src

** Hooks

User functions triggered on WM events. Handler errors are isolated: one
bad hook never breaks others or the WM.

#+begin_src lisp
(rhizome:add-hook :window-created
  (lambda (win) (format t "new: ~A~%" (rhizome:window-title win))))
#+end_src

Available hooks: =:window-created= (win), =:window-closed= (win),
=:focus-changed= (win), =:layout-changed= (output layout-name),
=:workspace-changed= (workspace output), =:output-created= (output).
Also: =remove-hook=, =clear-hook=, =list-hooks=, =run-hook=.

** IPC — the stumpish equivalent

A Unix domain socket (=$XDG_RUNTIME_DIR/rhizome.sock=) accepts one
command per line and replies with the result. The =rhizome-cmd= helper
(in ~~/.local/bin/~) sends commands from the shell or scripts:

#+begin_src bash
rhizome-cmd current-workspace
rhizome-cmd switch-workspace 3
rhizome-cmd "(* 6 7)"          # Lisp forms evaluate in the live image
rhizome-cmd list-windows
rhizome-cmd toggle-bar
rhizome-cmd quit               # stops the WM; river keeps running
#+end_src

Commands run on the WM's main thread (the socket thread only moves
bytes), so no Wayland request is ever made from a foreign thread.
Available commands include everything in the command table
(switch-workspace, current-workspace, toggle-bar, screenshot,
list-windows, quit, focus-next/previous, switch-layout) plus arbitrary
Lisp forms. The bar's workspace numbers use this socket to switch
workspaces on click.

** SLIME integration

The WM starts a swank server on =127.0.0.1:4005= (configurable via
=(:swank (:port 4005))=) — =M-x slime-connect= from Emacs gives a REPL
into the live window manager: redefine layouts, inspect windows, hot-patch
anything, while it runs. Disable with =(:swank (:enabled nil))=.

** Prefix key (Ctrl+T) — StumpWM-style keychains

River's keybindings are single-key+modifier registrations, so multi-key
chains cannot be one binding. Rhizome solves this StumpWM-style: the
prefix (Ctrl+T) is a normal binding; pressing it opens an invisible
keyboard-exclusive capture surface, and follow-up keys dispatch through
a client-side keymap state machine (prefix.lisp) — the same wl_keyboard
path the interactive prompts use. A transient "C-t -" message shows the
chain is active.

** Message window and interactive prompts

Transient on-screen messages (the StumpWM message-window equivalent):
workspace switches echo their number, =rhizome-cmd= results appear
briefly on screen, and =(rhizome:message "fmt" args)= shows anything
else. Messages auto-hide after 3 seconds.

The generalized input prompt (prompt.lisp) provides filtering and
selection, powering three interactive clients:

- =MOD+W= — window list: pick by title, jump to the window's
  workspace and focus it
- =MOD+G= — workspace picker
- =MOD+X= — command palette (run any command from the command table)

Type to filter, Up/Down or Tab to select, Enter to complete, Escape to
cancel. The same engine is available for extensions — most directly
through the scripting menu (StumpWM's select-from-menu):

#+begin_src lisp
;; from config.lisp or the REPL: pop a menu, act on the choice
(rhizome:select-from-menu "Workspace?"
  (list (cons "Web"  (lambda () (rhizome:switch-workspace 2)))
        (cons "Code" (lambda () (rhizome:switch-workspace 3)))))
#+end_src
=(rhizome:prompt-open "Title:" :candidates '(...) :on-complete #'f)=.

** Workspaces

Nine StumpWM-style workspaces per output. Windows open on the current
workspace; =MOD+1..9= switches workspaces, =MOD+Shift+1..9= moves the focused
window (and follows it). Windows on other workspaces are hidden and reappear
on return. The current workspace is shown in the bar's =:workspaces=
module with the active number underlined in the accent color,
occupied workspaces in the foreground color, empty ones muted, and
configurable breathing room between numbers
((:bar :workspaces :gap 8), default 8px). The WM exports its
state (layout, window count, workspace, per-workspace occupancy,
focused title) to the bar via an atomic snapshot file,
~~/.cache/rhizome/snapshot.sexp~.

** Status bar

A configurable status bar / mode-line, rendered in CL via layer-shell. Runs as
its own process (the compositor / WM / bar as cooperating processes — river's
philosophy applied to the bar too), driven entirely from the configuration.
Since river reports full output dimensions to the WM even when the bar has an
exclusive zone, the WM reserves the bar's space itself in its layout math.

#+begin_src lisp
;; Live from the REPL or in ~/.config/rhizome/config.lisp:
(rhizome:configure '(:bar (:enabled nil)))          ; disable the bar
(rhizome:configure '(:bar (:modules (:left (:layout :windows)
                                        :center (:clock)
                                        :right (:network :volume :battery)))))
(rhizome:configure '(:modules (:clock (:format "%a %d %b %H:%M"))))
(rhizome:reload-config)                             ; reset + reload user file
#+end_src

Bar modules: =:workspaces= (numbers — active underlined in accent,
occupied in foreground, empty muted, with per-number gaps),
=:layout= (current layout), =:windows= (window count), =:focused=
(focused window title), =:recording= (a red =REC= marker while any
screen capture session is active — river v5 =capture_sessions=,
colors via =:bar :recording-color=), =:clock= (strftime-like
format), =:battery= (/sys), =:volume= (wpctl), =:network=
(nmcli). Each rate-limited
module takes an =:interval= (seconds). The bar's own
=:bar :interval= (default 0.15s) is the poll rate for change
detection: the bar re-renders only when a module's output actually
changed, so workspace switches and volume changes appear within one
poll.

Modules are clickable: the bar process binds a =wl_pointer= and records each
module's rendered area as a click target. Modules can define shell-command
actions in the config — =:on-click=, =:on-scroll-up=, =:on-scroll-down=.
Defaults: clicking the volume module opens pavucontrol (scrolling adjusts it
by 5%); clicking the network module opens nm-connection-editor. These
targets are plain shell commands — any application works, e.g.:

#+begin_src lisp
(rhizome:configure
  '(:modules (:volume (:on-click "pavucontrol")
              :network (:on-click "nm-connection-editor"))))
#+end_src

The bar also renders application icons with click actions —
launcher-style, with real PNG icons decoded and alpha-blended into
the shm buffer:

#+begin_src lisp
(rhizome:configure
  '(:bar (:modules (:left (:layout :windows
                                (:icons ((:icon "flameshot" :on-click "flameshot gui")
                                         (:icon "variety" :on-click "variety")
                                         (:icon "/path/to/custom.png" :on-click "rhizome-cmd lock"))))
                     :center (:clock)
                     :right (:volume :network :battery)))))
#+end_src

=:icon= is an icon name (searched in the hicolor theme directories,
PNG only) or an absolute path; icons render at 16x16 and each carries
its own =:on-click= / =:on-scroll-up= / =:on-scroll-down= actions
through the same hitbox chain as text modules.

The target applications are user choices, not hard dependencies —
see the optional package list above. The user config file lives at
~~/.config/rhizome/config.lisp~; the bar process logs to
~~/.cache/rhizome/bar.log~. MOD+B toggles the bar.

** Native application launcher (MOD+D)

The launcher is a native Wayland layer-shell overlay — no external process like fzf or rofi needed. It uses =zwlr_layer_shell_v1= + =river_layer_shell_v1= to create a top-layer popup with exclusive keyboard interactivity.

Features:
- Scans XDG =.desktop= files from standard directories (=XDG_DATA_HOME=, =XDG_DATA_DIRS=, =~/.local/share/applications=, =/usr/share/applications=)
- Filters out =NoDisplay=, =Hidden=, and non-Application entries
- Strips Exec field codes (=%f=, =%u=, =%F=, etc.) and wraps Terminal=true apps in Alacritty
- TrueType text through the theming engine (font.lisp; 8x16 bitmap fallback without freetype)
- Colors entirely from the =:launcher= config group (see Theming below)
- Substring search filtering with live redraw
- Scrollable list with client-side key repeat (hold down arrow to scroll)
- Keyboard: type to filter, Up/Down to navigate, Enter to launch, Escape to close, Backspace to delete
- Reuses shm buffer across redraws for fast rendering (no per-frame mmap/munmap)

** Theming (fonts and colors)

All drawn surfaces — bar, message window, prompts, launcher, and
window borders — are themed through the config system. Fonts render
with real TrueType via libfreetype (resolved through fontconfig, so
plain family names work and a missing family falls back to the
system's best match); when freetype or fontconfig is unavailable
everything degrades to the built-in 8x16 bitmap font with the
original metrics.

#+begin_src lisp
(rhizome:configure
  '(:theme (:font-family "JetBrains Mono"   ; any fc-match name
            :font-size 14
            :focused-border "#7aa2f7"
            :unfocused-border "#404040")))
(rhizome:configure
  '(:launcher (:background "#23142d"
               :prompt-color "#8c64aa"
               :query-color "#dcc8f0"
               :cursor-color "#b4a0d2"
               :selection-background "#503278"
               :selected-color "#f0e6ff"
               :entry-color "#aa96c8")))
#+end_src

The bar's own colors live under =:bar= (=:background=, =:foreground=,
=:accent=, =:muted= — already supported by the module renderer's
per-part hex colors). The workspace module's spacing is
(:bar :workspaces :gap 8) (default 8px). Changing =:theme= font keys
re-resolves the font in the WM process live; the bar restarts (as
with any bar affecting change) and picks the new font up at startup.
Text widths are per-glyph advances now, so the bar centers the clock
exactly and the launcher cursor hugs the typed query.

Module parts can carry render flags: =:gap N= (extra pixels after
the part) and =:underline t= (a 2px line in the part's color under
the text) — the mechanism behind the active-workspace underline.
The launcher's selected row carries a 3px accent edge
((:launcher :accent ...)). A complete, commented configuration
covering every group lives in =examples/config.lisp=.

* Frame trees (the StumpWM layout model)

The screen is a recursive binary tree of frames (frames.lisp) — the
StumpWM core data structure. Internal nodes are splits; leaves are
frames holding windows, one visible at a time:

- Every workspace starts as a single full-screen frame; carve it up
  with =C-t s= (side-by-side) and =C-t S= (stacked), merge back with
  =C-t R=. The current window stays put on a split; the next window
  opened lands in the new frame.
- =C-t= arrows move focus between frames; =C-t n= / =C-t p= cycle
  the windows inside the current frame; =rhizome-cmd resize-split
  30= nudges a dividing line.
- New windows open into the current frame; closed windows leave the
  frame behind — the layout is yours and it stays.
- Layout NAMES are frame-tree templates that rebuild the workspace's
  tree: =:monocle= (one frame), =:master-stack= (master + stack),
  =:even= (grid with a cell per window). Custom layouts defined with
  =define-layout= become tree leaves too (their placements must
  partition the screen; otherwise the workspace falls back to one
  frame). User splits persist until the next =switch-layout=.

** Layout templates

| Name          | Shape                                        |
|---------------+----------------------------------------------|
| =master-stack= | One master frame on the left, stack on the right (default) |
| =even=        | Grid with a frame per window                 |
| =monocle=      | One frame filling the screen                  |

** Defining custom layouts

#+begin_src lisp
(rhizome:define-layout :my-layout (windows width height)
  ;; Your tiling logic here
  ;; Must return a list of (window x y w h) tuples
  ;; that tile the screen — the rectangles become frames
  (loop for win in windows
        for i below (length windows)
        collect (list win 0 (* i (floor height (length windows)))
                      width (floor height (length windows)))))
#+end_src

* Session: locking and logging out

The locker is a configurable external program — =swaylock= by default
(=sudo pacman -S swaylock=; hyprlock and friends work too):

#+begin_src lisp
(rhizome:configure
  '(:lock (:command "swaylock"
           :args ("--daemonize")
           :idle-seconds 300)))   ; swayidle auto-lock; 0 = off
#+end_src

MOD+Shift+L locks now; =rhizome-cmd lock= too. With =:idle-seconds=
set, the WM spawns =swayidle= at startup and locks after that many
seconds of inactivity.

MOD+Shift+E (or =rhizome-cmd logout=) ends the river session and
returns to the display manager's greeter — press twice within three
seconds to confirm. Logout goes through the protocol itself:
=river_window_manager_v1.exit_session= (v4+), the compositor's own
session-exit path — the XML says WMs "should only make this request
if the user explicitly asks to exit the Wayland session", which is
exactly what the double-press confirm guards. River sends the WM its
finished event and both shut down cleanly. (Rivers bound below v4
get SIGTERM — river's clean-shutdown signal — as a fallback.) The
session script then stops rhizome-session.target, releasing the
systemd graphical session (piece 4) before the greeter returns.

=rhizome-cmd detach= is logout's sibling: it stops rhizome WITHOUT
ending the session — river's WM hot-swap. Placements of
identifier-bearing windows are remembered, the bar stops (and its
supervisor stands down), in-process surfaces close, and rhizome
sends =river_window_manager_v1.stop=, waits for =finished=, destroys
the manager, and exits. The session stays up with windows frozen
in place; anything speaking =river-window-management-v1= can bind
and take over live — including a freshly built rhizome:

#+begin_src bash
sbcl --eval '(ql:quickload :rhizome)' --eval '(rhizome:run)' &
#+end_src

* Floating windows

Not everything belongs in a tiling grid: GIMP toolboxes, palette
dialogs, and picture-in-picture video want to keep their own size and
be moved around freely. Rhizome handles these StumpWM-style as floats
(floating.lisp):

- A floating window keeps its own position and dimensions; the tiling
  layouts never see it, and it stacks above the tiling (the focused
  float renders on top).
- On first float the window is told it is NOT part of the tiling
  (=river_window_v1.set_tiled= none), so it draws its own shadows and
  decorations, and =propose_dimensions= 0x0 lets it pick its own
  size — a GIMP toolbox comes up exactly as GIMP intends.
- Titlebar dragging works: clients request interactive moves and the
  =river_seat_v1= pointer-op protocol carries the cumulative motion;
  resizes are clamped to the window's own min/max size hints, and a
  float can never be dragged fully off-screen (a ~30px strip stays
  reachable).
- MOD+Left-drag moves any window — a dragged tiled window floats
  first, StumpWM-style; MOD+Right-drag resizes from the bottom-right.
- Floats live on workspaces like everything else: switching hides and
  restores them with the rest.

Toggle the focused window with =C-t f= or =rhizome-cmd toggle-float=;
float apps automatically with a window rule:

#+begin_src lisp
(rhizome:configure
  '(:window-rules ((:match "gimp" :float t))))
#+end_src

Rules match =:key :app-id= (default), =:title=, =:any=, or
=:identifier= (river v4's stable window IDs). Windows WITH an
identifier are also *remembered*: their workspace and float state
persist across WM restarts and relogins
(~/.local/share/rhizome/window-state.sexp=), restored before rules
run so explicit rules still win. Disable with
=(configure '(:window-state (:enabled nil)))=.

Maximize is float-based too: a client's =maximize_requested=
(terminal full-grid, browser buttons) is honored as a float covering
the output's usable area — bar strip excluded — and =unmaximize_requested= restores the exact prior state (tiled windows
return to the grid, floats get their own geometry back). Size hints
still clamp, so fixed-size dialogs never stretch. Toggle the
focused window with =rhizome-cmd maximize=; the audit trail is in
the [[Protocol coverage audit][protocol audit]] above.

From the REPL: =(rhizome:float-window win)=, =(rhizome:unfloat-window win)=,
=(rhizome:toggle-float win)=, =(rhizome:toggle-maximize win)=.

* A note on dependencies: why we implement DBus ourselves

Rhizome stays a pure Common Lisp application — the DBus wire
protocol is implemented locally in =dbus.lisp= (SASL EXTERNAL auth,
signature parsing, alignment-aware marshalling, message framing,
reader thread with reply matching), reusing the same minimal CFFI
socket shims as =ipc.lisp=.

Why not an existing library? Death's =dbus= (the only pure-CL client
on Quicklisp) was evaluated first and rejected:
1. *It does not build here* — its iolib dependency fails its CFFI
   grovel step (=lfp.h= missing) on this system, so it cannot even
   be loaded.
2. *It is client-oriented* — hosting a service (owning a well-known
   name, receiving method calls, emitting signals), which is exactly
   what a StatusNotifierWatcher needs, is beyond its comfortable
   envelope.
3. *Dependency philosophy* — pulling iolib/babel/cxml/ieee-floats
   for functionality we can implement in ~700 lines contradicts the
   zero-quicklisp-deps rule =cos=, =filters= and =ipc.lisp= already
   follow (UTF-8 and IEEE-754 doubles are local too).

The implementation was pinned byte-for-byte against gdbus's actual
wire traffic (captured via an LD_PRELOAD write interposer) —
including two real-world subtleties the spec does not make obvious:
the SASL BEGIN line must end =\r\n= (a bare =\n= leaves
dbus-broker mid-handshake and it silently drops everything after),
and an array's declared length must NOT include the final element's
alignment padding (that padding belongs to the enclosing message;
dbus-broker rejects the padded form).
- [X] Window selection expressions (WSE, wse.lisp):
      (:and (:app-id \"emacs\") (:title \"docs\")) over app-id,
      title, number, workspace, float, marked, focused; wse-windows /
      wse-map / wse-count for scripting, window rules accept :wse in
      place of :match, rhizome-cmd wse <expr> reports matches
- [X] Niri-style scrollable tiling (C-t v): a horizontal ribbon
      where every window owns a full-height column; C-t , / . move
      focus between columns with the viewport following (niri keeps
      focus visible), MOD+, / . scroll the viewport alone, new

- [X] Fuzzy search: prompts and the launcher match query characters

- [X] Switch modifier from Alt to Super on real hardware: the user

* Design vision

The long-term goal is a Wayland window manager that captures the spirit of the Lisp Machines:

- *Live programmability*: eval expressions from keybindings, redefine layouts at runtime, inspect and manipulate live window objects from the REPL
- *Native CL app launcher*: a fuzzel-like overlay rendered in CL, with fuzzy search, keyboard navigation, and programmable app list — no external process needed
- *Programmatic window placement*: window rules to place specific apps on specific outputs with specific sizes, like StumpWM's =define-window-preference=
- *Hooks*: user-defined functions triggered on window creation, focus change, layout switch, output hotplug
- *Inspectable everything*: =(describe some-window)=, =(inspect some-output)=, eval expressions that manipulate live state
- *Mode line*: a status bar showing window state, layout, clock — rendered in CL via layer-shell
